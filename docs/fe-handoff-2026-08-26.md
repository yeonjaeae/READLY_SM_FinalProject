## 1. 채팅방 활성화 시간 (신규 제약)

**메시지 전송은 모임 시작 15분 전부터, 모임(30분)이 끝난 15분 뒤까지 총 60분 동안만 된다.**
기준은 모임 생성 시 지정한 `date` + `time`이다.

- 이 판정은 **백엔드에서만** 한다. 프론트가 상태를 받아 관리할 필요도, AI 서버가 알 필요도 없다.
  화면에서 입력창을 잠그는 것은 UX 개선일 뿐이고, 잠그지 않아도 서버가 거부한다.
- **조회는 제한이 없다.** 모임이 끝난 뒤에도 `GET /api/book-clubs/{clubId}/chats`로 최근 7일치 대화를 볼 수 있다.
  즉 "끝난 방에 들어가서 대화를 다시 읽는" 화면은 그대로 동작한다.

거부될 때 오는 메시지(그대로 노출해도 되는 문구다):

- 아직 열리기 전: `아직 채팅방이 열리지 않았습니다. 모임 시작 15분 전부터 이용할 수 있습니다.`
- 이미 닫힌 뒤: `채팅방이 종료되었습니다. 지난 대화는 계속 확인할 수 있습니다.`

전송 경로별 거부 방식:

| 경로 | 거부 방식 |
| --- | --- |
| STOMP `SEND /pub/chat/clubs/{clubId}` | 메시지가 발행되지 않고, **보낸 사람에게만** `/user/sub/errors`로 사유가 온다 (아래 2번) |
| REST `POST /api/book-clubs/{clubId}/meeting/assist` (방장 AI 호출) | **409** + `{ "message": "..." }` |

## 2. STOMP 전송 거부 알림 — `/user/sub/errors` 구독 (필수)

STOMP는 서버가 전송을 거부해도 클라이언트에 아무것도 보내지 않는다. 그래서 **보낸 사람 전용 경로**를 새로 만들었다.
`src/api/chatSocket.js`의 `onConnect` 안에 구독을 하나 더 넣으면 된다.

```js
// 기존 구독은 그대로 두고 아래를 추가
client.subscribe("/user/sub/errors", (message) => {
  const { message: reason } = JSON.parse(message.body);
  onSendRejected?.(reason);   // 예: alert(reason) 또는 채팅창 상단 안내
});
```

- 페이로드는 `{ "message": "..." }` 하나뿐이다.
- 이 경로는 **자기 자신에게만** 전달된다. 다른 참여자에게는 가지 않는다.
- `/user`는 STOMP의 사용자 전용 목적지 접두사다. 구독 문자열을 그대로 `"/user/sub/errors"`로 쓰면 된다.
- 구독하지 않아도 동작에는 문제가 없지만, **전송 실패가 화면에서 조용히 사라진다.**
  지금 `sendChatMessage`는 publish만 하고 결과를 모르기 때문에, 사용자는 메시지가 증발한 것으로 보인다.

## 3. AI 호출 응답 시간 (최대 2분)

AI 서버가 LLM 응답을 만들고, 무료 플랜에서는 콜드 스타트까지 겹쳐 응답이 수십 초 걸린다.
백엔드 타임아웃을 **10초 → 120초**로 늘렸다(연결 10초).

- 영향받는 호출: `POST /api/book-clubs/{clubId}/meeting/assist`(방장 AI 진행자),
  `POST /api/notes/books/{bookId}/ai-generate`(AI 독후감).
- 지금 `apiFetch`에는 클라이언트 타임아웃이 없어서 그냥 기다린다. 다만 화면에서는
  **버튼 비활성화 + 로딩 표시**가 없으면 사용자가 여러 번 누르게 된다(누르는 만큼 AI 요청이 나간다).
- 방장 AI 호출의 결과는 응답 바디가 아니라 **채팅 브로드캐스트로 도착한다**(기존과 동일).
  `MeetingRoom.js`가 이미 그렇게 처리하고 있어 로직 변경은 필요 없다.
- 타임아웃이 나면 기존과 같이 **503** + `AI 서버에 연결할 수 없습니다. 잠시 후 다시 시도해 주세요.`

## 4. AI 독후감 생성이 이제 실제로 동작한다

`POST /api/notes/books/{bookId}/ai-generate`는 그동안 **항상 503**이었다. 우리가 AI 서버에 보내는
필드명이 달라서(`bookTitle` vs `book_title`) AI 서버가 422로 거절했기 때문이다. 이번에 맞췄다.

- 이제 200이 오고, `GET /api/notes/books/{bookId}/ai-note`로 실제 AI가 쓴 본문을 읽을 수 있다.
- **`tags`는 계속 빈 배열로 온다.** 현재 AI 서버 응답에 태그가 없다. 태그 UI가 있다면 빈 값을 전제로 그려야 한다.
- 응답 형식은 바뀌지 않았다: `{ exists, aiNoteId, content, tags[], edited }`.

## 5. 서버 내부 변경 (프론트 영향 없음)

확인만 하고 넘어가면 되는 것들이다. 경로·요청·응답 형식이 전부 그대로다.

- **채팅 브로커에서 Kafka를 걷어내고 Redis Pub/Sub으로 바꿨다.** 실시간 흐름과 페이로드는 동일하다.
- **채팅 보관 정책**: Redis에 7일 보관(조회 대상), 만료되면 PostgreSQL로 옮겨 30일 더 보관 후 삭제.
  **보관본을 읽는 API는 없다.** 프론트가 보는 대화는 언제나 Redis에 있는 최근 7일치다.
- **AI 자동 개입은 현재 꺼져 있다.** AI 서버에 `/api/ai/chat`이 없어 채팅마다 404가 나던 호출을 잠시 막아 뒀다.
  따라서 AI는 **방장이 버튼을 눌렀을 때만** 말한다. AI 서버가 그 경로를 제공하면 다시 켠다.
- 모임 목록 API의 인원수 조회 쿼리를 최적화했다(응답 동일).

## 6. 배포할 때

- `src/api/api.js`의 `API_BASE_URL`이 `http://localhost:8080`으로 하드코딩돼 있다.
  배포 빌드에서는 배포된 백엔드 주소를 봐야 한다(예: `process.env.REACT_APP_API_BASE_URL` 사용).
  `chatSocket.js`는 이 값에서 `ws://`를 만들어 쓰므로 여기만 바꾸면 소켓 주소도 따라간다.
- 백엔드는 `CORS_ALLOWED_ORIGINS` 환경변수에 프론트 배포 도메인을 넣어야 한다. 알려 주면 넣겠다.
- **브라우저에서의 실제 CORS/WebSocket 연결은 아직 확인하지 못했다.** 지금까지 검증은 Postman·Node 클라이언트로 했고,
  이 둘은 CORS를 적용받지 않는다. 프론트를 붙이는 첫 시도에서 문제가 나면 바로 알려 달라.

## 7. WebSocket 400 — 해결됨 (프론트 코드는 잘못이 없었다)

증상은 아래가 반복되는 것이었다.

```
WebSocket connection to 'wss://readly-backend.duckdns.org/ws/chat' failed:
Error during WebSocket handshake: Unexpected response code: 400
채팅 소켓이 연결되어 있지 않습니다.
```

원인은 **EC2의 nginx가 `Upgrade`/`Connection` 헤더를 백엔드로 넘기지 않은 것**이다.
두 헤더는 hop-by-hop이라 nginx가 기본적으로 프록시하지 않는다. 스프링까지는 요청이 도달하지만
업그레이드 요청으로 보이지 않아 `400 Can "Upgrade" only to "WebSocket".`을 냈다.
`proxy_http_version 1.1` + `proxy_set_header Upgrade/Connection`을 넣어 고쳤고,
2026-08-30 13:09(UTC) 재확인에서 `101 Switching Protocols`가 나왔다.

- **프론트가 고칠 것은 없다.** `chatSocket.js`의 `brokerURL` 방식(순수 WebSocket)이 맞고, 백엔드도 그대로다.
- "채팅을 보내도 내역이 바로 안 보인다"도 같은 원인이었다. 소켓이 안 붙으면
  `sendChatMessage`가 `client.connected`를 보고 경고만 찍고 발행하지 않는다(그 노란 경고가 그 줄이다).
  이제 붙으므로 실시간 표시도 함께 살아난다.
- `proxy_read_timeout`을 3600초로 잡았다. 조용한 방에서 60초마다 끊기던 문제는 없을 것이다.
  그래도 끊기면 stompjs의 `reconnectDelay: 3000`이 다시 붙는다.

## 8. 독서모임 상태에 `FULL`(모집완료)이 추가됐다 — 한 줄 필요

정원이 6명인 모임에 6명이 모였는데도 계속 "모집중"으로 보이는 문제가 있었다.
원인은 백엔드였다. `status`가 모임 생성 시 `PENDING`으로 저장된 뒤 **아무도 바꾸지 않았다.**
정원이 차든 모임이 끝나든 영원히 `PENDING`이었다.

이제 `status`는 저장된 값이 아니라 **조회할 때마다 인원과 모임 시각으로 계산해서** 내려간다.

| 값 | 라벨 | 조건 |
| --- | --- | --- |
| `PENDING` | 모집중 | 모임 시작 전 + 자리 남음 |
| `FULL` | **모집완료** | 모임 시작 전 + 인원 == 정원 (**차는 즉시**) |
| `IN_PROGRESS` | 모임중 | 시작 15분 전 ~ 종료(시작+30분) 15분 후 |
| `COMPLETED` | 종료 | 그 뒤 |

시각 판정이 인원 판정보다 우선이다. 정원이 찬 모임도 시작 시각이 되면 `IN_PROGRESS`로 넘어간다.

**프론트 변경 (한 줄)** — `src/api/api.js`의 `statusLabel`:

```js
export function statusLabel(status) {
  if (status === "PENDING") return "모집중";
  if (status === "FULL") return "모집완료";   // ← 추가
  if (status === "IN_PROGRESS") return "모임중";
  if (status === "COMPLETED") return "종료";
  return status;
}
```

- 없으면 뱃지에 문자열 `"FULL"`이 그대로 나온다(`statusLabel`의 마지막 `return status` 때문).
- **응답 필드 구성은 그대로다.** 필드 추가·삭제 없고 `status`가 가질 수 있는 값만 늘었다.
- `Community.js`가 라벨 문자열(`"모임중"`)로 뱃지 클래스를 고르는 부분은 영향 없다.
  "모집완료"에 별도 스타일을 주고 싶으면 그때 분기를 추가하면 된다.
- 프론트에서 `currentMemberCount >= maxCapacity`를 직접 계산할 필요는 없다.
  서버가 가입을 거절하는 조건과 같은 식으로 판정하므로, 화면과 실제가 어긋나지 않는다.
- **아직 배포 전이다.** 백엔드 작업 트리에만 있고 커밋·배포되지 않았다.
  배포 전에 프론트가 먼저 고쳐도 `FULL`이 오지 않을 뿐이라 깨지지 않는다.
